# skill-authoring — 스킬에는 지시만 쓴다

## 두 종류

쓰기 전에 어느 쪽인지 정한다.

| 종류 | 무엇 | 예 |
|---|---|---|
| 방법론 스킬 | 어떤 일을 어떻게 하는가. 하네스 없이도 성립한다 | `debugging`, `spec-authoring`, `research` |
| 도구 스킬 | 하네스의 장치를 움직이는 절차. 에이전트를 부르고, 스크립트·원장·상태 파일을 다룬다 | `orchestration`, `unattended` |

- 도구 스킬은 에이전트 이름을 쓴다. 누구를 부르는지, 무엇을 넘기는지, 무엇을 돌려받는지가 절차다
- 방법론 스킬은 에이전트 이름을 쓰지 않는다. 필요하면 역할로 쓴다("검증하는 쪽", "만드는 쪽")
- 다른 스킬 이름은 두 종류 모두 쓰지 않는다
- 아래의 넣는 것·빼는 것은 두 종류에 같이 적용한다

## 넣는 것

| 종류 | 예 |
|---|---|
| 절차·순서·조건 | "1. 재현한다 2. 원인을 찾는다 3. 고친다 4. 증명한다" |
| 금지 | "테스트를 조건에 맞게 고쳐 통과시키지 않는다" |
| 형식·골격·표·명령어·예시 | 보고서 골격, 명령 블록, 채워진 예시 |
| 판정 기준 | "실행 검증과 산출물 대조만 완료로 친다" |
| 흔한 실패 표 | 증상 → 원인 |

## 빼는 것

| 유형 | 알아보는 법 | 예 |
|---|---|---|
| 동기·근거 | 규칙 뒤에 "~하면 ~된다", "~이기 때문이다", "~보다 싸다"가 붙는다 | "재현이 안 되면 고칠 수 없고 고쳤는지도 알 수 없다" |
| 검증할 수 없는 구호 | 참·거짓을 확인할 방법이 없다 | "문서는 코드보다 오래 산다" |
| 다른 스킬 이름 | 본문이나 description에 다른 스킬 이름이 나온다 | "세부는 `verify-loop`" |
| 에이전트 이름 (방법론 스킬만) | 방법론 스킬에 에이전트 이름이 나온다 | "모르면 `investigator`에게 묻는다" |
| 저장소 고유 서사 | 다른 프로젝트에 옮기면 말이 안 된다 | "이 하네스는 사용자가 옆에 있다고 전제한다" |
| 대화에서 옮긴 설명 | 지시가 아니라 사용자와 나눈 이야기의 요약이다 | 사용자의 말투나 표현이 그대로 들어간 문장 |

문장마다 "이것은 무엇을 어떻게 하라는 지시인가"에 답이 있으면 남기고, 없으면 뺀다.

다른 스킬 이름을 지웠을 때 지시까지 사라지면, 이름만 빼고 지시를 문장으로 풀어 쓴다.

```
전: 보고서는 `completion-evidence` 형식으로 쓴다
후: 보고서에는 완료 기준마다 증거 수준을 적은 표를 쓴다
```

여러 스킬이 같은 규칙(문서 위치, 보고 형식)을 따라야 하면 그 규칙을 스킬 하나에 두고, 그 스킬을 쓰는 에이전트가 시작할 때 불러오게 한다. 다른 스킬 본문에는 적지 않는다.

## 이름

- 하는 일의 이름으로 짓는다. `orchestration`, `research`, `debugging`, `plan-and-check`
- 역할 이름으로 짓지 않는다. `orchestrator`, `researcher`, `reviewer`는 에이전트나 세션이 맡는 역할이다
- kebab-case 영문

## description

- 언제 쓰는지와 무엇을 하는지를 쓴다. 사용자가 할 법한 요청 문구를 따옴표로 넣는다
- 쓰지 않는 경우를 적는다
- 본문과 같은 잣대를 적용한다. 다른 스킬 이름, 구호, 근거를 넣지 않는다

## 제목 줄

`# <이름> — <한 줄>`. 한 줄은 명령형 규칙으로 쓰거나 비운다.

```
씀:   # debugging — 원인을 알기 전에 고치지 않는다
안 씀: # interface-contract — 소통을 문서로 바꾼다
```

## frontmatter

- 필드는 `name`, `description`
- 값 안에 콜론+공백(`: `)이 있으면 값 전체를 작은따옴표로 감싼다. 값 안의 작은따옴표는 두 개(`''`)로 쓴다
- 쓰고 나서 YAML 파서로 읽어 본다

## 파일 나누기

- `SKILL.md`에는 절차와 판정 기준을 둔다
- 길어지는 형식·표·예시는 `references/<주제>.md`로 빼고 `SKILL.md`에서 경로로 가리킨다
- 반복하는 계산·검사는 `scripts/`에 둔다. 표준 라이브러리만 쓴다
- 스킬 밖의 경로(다른 스킬 디렉터리, 저장소 문서 위치)를 적지 않는다

## 도구·런타임 동작에 대한 문장

"~는 반영되지 않는다", "~는 세션 시작 때 고정된다", "~는 시작 시 로드된다"처럼 도구의 동작을 단정하는 문장은 실험이나 공식 문서로 확인한 것만 쓴다. 확인하지 않았으면 쓰지 않는다.

## 규칙이 생긴 이유

스킬에 쓰지 않는다. 변경 기록(CHANGELOG)에 쓴다. 사유에는 요청한 사람이 말한 이유만 적고, 추측한 이유는 적지 않는다.

## 쓰고 나서

1. 문장마다 "넣는 것 / 빼는 것" 표에 대어 본다
2. 전체 스킬 이름 목록으로 본문과 description을 검색해, 다른 스킬 이름이 없는지 본다
3. 방법론 스킬이면 에이전트 이름 목록으로도 검색한다
4. frontmatter를 YAML 파서로 읽어 본다

## 흔한 실패

| 증상 | 원인 |
|---|---|
| 머리말이 깨지거나 description이 중간에서 잘림 | 따옴표 없는 값에 `: ` |
| 스킬 하나를 다른 프로젝트로 옮기니 말이 안 됨 | 저장소 고유 서사, 다른 스킬 이름, 방법론 스킬 안의 에이전트 이름 |
| 도구 스킬에서 에이전트 이름을 지워 누구를 부르는지 모르게 됨 | 두 종류를 구분하지 않고 방법론 기준을 적용 |
| 스킬 이름이 사람처럼 읽힘 (`-er`, `-or`) | 하는 일이 아니라 맡는 역할로 지음 |
| 규칙 하나에 근거 문장이 두세 개 붙음 | 사유를 변경 기록이 아니라 본문에 씀 |
| 사용자의 말투가 스킬에 그대로 있음 | 대화를 요약해 옮김 |
| 도구 동작을 단정했는데 틀림 | 확인 없이 씀 |
