# agent-authoring — 에이전트 정의에는 배선과 역할 계약만 쓴다

## 배선 — frontmatter

| 필드 | 쓰는 법 |
|---|---|
| `name` | 역할 이름. kebab-case. `reviewer`, `architect`, `investigator` |
| `description` | 언제 부르는지, 무엇을 하는지, 무엇을 하지 않는지. 비슷한 에이전트와의 경계 |
| `tools` | 역할에 필요한 도구만. 검토·비판·조사 역할에는 `Edit`를 주지 않는다. `Write`는 자기 결과 파일 하나만 쓰는 역할에 준다 |
| `model` | `inherit` 또는 모델 지정 |
| `skills` | 시작할 때 불러올 스킬 이름 목록. 여러 에이전트가 따라야 하는 공통 규칙(문서 위치, 보고 형식)은 여기서 건다 |

- 값 안에 콜론+공백(`: `)이 있으면 값 전체를 작은따옴표로 감싼다. 값 안의 작은따옴표는 두 개(`''`)로 쓴다
- `skills`에 적은 스킬이 없거나 꺼져 있으면 경고와 함께 건너뛴다. 이름을 실제 스킬 디렉터리 이름과 대조한다
- 플러그인 안에서 스킬과 에이전트는 `<플러그인>:<이름>`으로 노출된다. 같은 플러그인의 스킬을 `skills`에 적는 형식은 공식 문서에 없다. 확인 전에는 `skills` 대신 본문에서 스킬을 부르게 하고, `tools`에 `Skill`을 넣는다

## 역할 계약 — 본문

| 절 | 내용 |
|---|---|
| 첫 문단 | 무엇을 하는가 한두 문장 |
| 원칙 | 번호 목록. 하는 것과 하지 않는 것 |
| 절차 | 순서가 있으면 |
| 호출의 종류 | 같은 에이전트를 다른 목적으로 부르면 목적별로 |
| 보고 | 어디에 쓰고, 마지막 응답에 무엇만 옮기는가 |
| 멈춰야 하는 신호 | 진행하지 말고 보고할 조건 |
| 하지 않는 것 | 목록 |

다른 에이전트와 스킬의 이름은 쓴다(부를 에이전트, 불러올 스킬, 쓸 곳). 역할 대비 한 줄("검토자는 기준을 의심하지 않고, 비판자는 기준 자체를 의심한다")도 쓴다.

## 넣지 않는 것

| 유형 | 예 |
|---|---|
| 실제 사고 서사 | "파일이 다 있어 보여도 한 번도 빌드해 본 적이 없을 수 있다" 같은 지난 사고 이야기 |
| 이 에이전트가 생긴 사유 | "나눠 주면 각자 반만 알고 고른다. 그래서 하나다" |
| 구호 | "반박 불가능한 비판은 비판이 아니다" |
| 규칙에 붙은 근거 꼬리 | "~하면 그 위에 만든 것이 전부 무효가 된다" |

규칙이 생긴 이유는 변경 기록(CHANGELOG)에 쓴다.

## 도구·런타임 동작에 대한 문장

"~는 시작 시 로드돼 있다", "~는 반영되지 않는다"처럼 도구의 동작을 단정하는 문장은 실험이나 공식 문서로 확인한 것만 쓴다. 확인하지 않았으면 쓰지 않는다.

## 쓰고 나서

1. 문장마다 역할 계약인지, 넣지 않는 것인지 대어 본다
2. `tools`를 역할과 대어 본다. 고치지 않는 역할에 편집 도구가 없는지
3. `skills`의 이름을 실제 스킬 디렉터리와 대조한다
4. frontmatter를 YAML 파서로 읽어 본다

## 흔한 실패

| 증상 | 원인 |
|---|---|
| 검토 역할이 산출물을 고쳐 놓음 | `tools`에 `Edit` |
| 공통 규칙이 에이전트마다 본문에 복사돼 서로 어긋남 | `skills`로 걸 수 있는데 본문 텍스트로 전달 |
| 정의에 "지난번에 ~해서" 류 문장 | 변경 사유를 정의에 씀 |
| description만 보고 어느 에이전트를 부를지 모름 | 무엇을 하지 않는지, 비슷한 에이전트와의 경계가 없음 |
| 불러온다고 적은 스킬이 실제로 안 불러와짐 | `skills`의 이름 오타, 또는 플러그인 이름공간 |
